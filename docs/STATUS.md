The requirement carried forward from Phase 0's adversarial review — `source_listing_revisions` has no DB-level uniqueness on `(sourceListingId, meaningfulContentHash)` (removed deliberately — see `src/db/schema/source-listings.ts`; a lifetime-unique index would reject a listing whose content legitimately reverts to an earlier hash), so retry-safe idempotency has to be enforced in the write path itself — is now implemented: `src/db/write-source-listing-revision.ts`'s `writeSourceListingRevision` insert-or-ignores the listing row, then `SELECT ... FOR UPDATE`s it, re-reads its current revision's hash under that lock, and only inserts a new revision (then repoints `currentRevisionId`) if the freshly observed hash differs — all inside one transaction. Proven by a real concurrency test in `src/db/write-source-listing-revision.test.ts` (two `Promise.all`-raced calls for the same new listing collapse to one revision), which is why CI now runs a Postgres service (`.github/workflows/ci.yml`) rather than only verifying DB behavior by hand as Phase 0 did.

- [x] Crawl orchestrator implemented — `src/adapters/jobs-ge/crawl.ts`'s `runJobsGeCrawl` wires every piece above together for real: `startCrawlRun` → walk `/ge/ads/?page=N` to discovery's natural stop (or `MAX_DISCOVERY_PAGES`'s safety cap) → fetch and parse every discovered listing's detail page → `writeSourceListingRevision` → `expireOverdueListings` → `closeMissingListings` → `finishCrawlRun`. Every fetch (discovery pages and detail pages alike) is recorded as a resource + fetch attempt regardless of outcome, per concept §21.1. A per-listing fetch/parse failure never aborts the whole run (one bad detail page is routine, not catastrophic) — a fetch failure counts via `failedCount`, a parse failure via `quarantinedCount` (see below); an unexpected error from the write path itself aborts the run (marked `failed`) and rethrows, rather than continuing against what might be a broken DB connection. `fullCoverage` is asserted `true` at start (jobs.ge's Phase 1A crawl is always a full-corpus walk, never a deliberately-partial poll — §10.1's incremental-discovery optimization remains deferred, see below); whether that attempt actually *succeeded* is decided separately by `status` after the walk finishes (or doesn't), which is what `closeMissingListings`'s own persisted-row check actually gates on. Also surfaced and fixed a real, previously-unaddressed gap: nothing in this codebase had ever inserted jobs.ge's own `sources`/`source_policies` rows into the database (every prior DB test used a throwaway random-UUID source instead) — `ensureJobsGeSourceSeeded` now does this idempotently at the start of every run.

  First adversarial review of this orchestrator (2026-09-05) returned 4 P1s, all fixed before merge — each is a real correctness/safety property worth recording, not just a drafting note:
  - **Discovery's stop condition compared the wrong thing.** The original "a page contributes zero new IDs against everything accumulated so far" logic would treat a single broken/empty mid-corpus response (a challenge page, a transient empty render at, say, page 15 of 19) as a legitimate stop too, silently truncating discovery while still reporting `complete: true` — which, combined with a floor comparing only total count, could pass `DEFAULT_MIN_EXPECTED_DISCOVERED_LISTINGS` and let a truncated run drive real reconciliation. Fixed: `discoverAllListings` now compares each page's own ID set directly against the *immediately preceding* page's, requiring them to be non-empty **and** exactly equal — the actual signal RECON_NOTES.md documents for jobs.ge's clamp-to-last-page behavior. Any other case (empty, different, broken) simply never satisfies the stop condition, leaving `complete: false` and the run `partial` — the safe direction to be wrong in. `DEFAULT_MIN_EXPECTED_DISCOVERED_LISTINGS` (100, ~56x margin below the real 5,647) remains as defense-in-depth against a total collapse this stronger check wouldn't itself catch (e.g. two consecutive identical small responses).
  - **A detail-fetch/parse failure could make a still-listed opportunity look missing.** A listing present in discovery but whose detail fetch or parse failed never had `writeSourceListingRevision` called, so its `lastSeenAt` never advanced — `closeMissingListings` has only `lastSeenAt` to judge "observed this run" by, so repeated transient failures would eventually close a listing that was never actually gone from the index. Fixed with a new, narrower function, `touchSourceListingSeen` (`src/db/write-source-listing-revision.ts`): records that a listing was seen in the index without a successful content fetch behind it — bumps `lastSeenAt`/resets `missingStreak` and reactivates a `missing_suspected` listing (which already has prior real content) but leaves a bare `discovered` listing `discovered` (no content yet, so no "active" claim) and never reopens `closed`/`expired` (that needs the stronger confirmed-reappearance evidence below). The orchestrator calls it on both failure branches.
  - **Reappearing listings never reopened.** Concept §13's lifecycle explicitly allows `closed`/`expired` → `active` on reappearance, and `crawl_runs.reopenedCount` existed from Phase 0 but nothing ever set it. `writeSourceListingRevision` deliberately never reactivated `closed`/`expired` on its own (a stray fetch from anywhere isn't strong enough evidence) — rather than changing that default (and its existing, already-reviewed tests), added an explicit opt-in: `options.allowReopen`, plus a `reopened` result field. The orchestrator passes `allowReopen: true`, since a full discovery walk that re-found and successfully re-parsed a listing's content *is* the confirmed-reappearance signal the original design withheld. `reopenedCount` is now tracked for real.
  - **Tests could have deleted real jobs.ge data.** `crawl.test.ts` originally ran every scenario against the real, fixed `jobsGeSource.id`, so `afterEach`'s `cleanupTestSource(jobsGeSource.id)` would delete every real jobs.ge row a shared dev database might already hold — the exact opposite of every other test file's random-UUID isolation. Fixed via `vi.mock('../../policies/jobs-ge.js', ...)` overriding only the `id`/`sourceId` fields to a random per-test-file UUID (baseUrl and the rest of the policy stay real, so URL construction and `isJobsGeUrlAllowed` behave exactly as in production) — plus a permanent regression assertion that `jobsGeSource.id` is never the real constant during tests.

  A second adversarial review pass returned 2 more P1s (P2s skipped per the project's severity-gate policy), both fixed:
  - **Overlapping crawls could double-count missing streaks.** Two runs for the same source in flight at once (a scheduler firing while a slow previous run is still going) could each independently reconcile the same absent listing against their own later `startedAt`, advancing `missingStreak` twice off overlapping observations rather than genuinely consecutive ones. Fixed at the database level, not with an application-side lock a connection pool would make unreliable to hold for a run's full (potentially hours-long) duration: a partial unique index, `crawl_runs_one_running_per_source_idx` (migration 0009), allows at most one `status = 'running'` row per source. `startCrawlRun` (`src/db/ingest.ts`) catches that specific constraint violation and raises a typed `CrawlAlreadyRunningError` — callers treat it as "skip this invocation," not a failure, since no run was actually created. Known, accepted limitation: a process that crashes hard enough to skip its own `finally`-style `finishCrawlRun('failed')` cleanup leaves a stale `running` row that blocks all future runs for that source until manually cleared — real stale-lock recovery is Phase 7 (operational telemetry/incident workflows) territory, not Phase 1A's.
  - **Detail-page parse failures weren't typed or quarantined.** concept §26's acceptance criteria explicitly require this, and folding a parse failure (the fetch succeeded; our parser couldn't extract the content — a markup/template mismatch) into the same `failedCount` as an ordinary network failure meant even a site-wide parser break would just look like a routine, mildly elevated failure rate. Fixed with `quarantineSourceListing` (`src/db/write-source-listing-revision.ts`, unconditionally overrides status to `quarantined` regardless of prior state — unreliable evidence takes precedence over any lifecycle nuance — and is itself excluded from every other function's reactivation allowlist here until a human resolves it) and `recordParserIncident` (`src/db/ingest.ts`, writes a `parser_incidents` row — the durable record concept §22's supervised-repair flow expects). The orchestrator's parse-failure branch now quarantines the listing and its resource, records the incident (kind `field_missing`, severity `warning`, evidence including the parser version and raw error), and counts it via `quarantinedCount` — distinct from `failedCount`, which is now fetch-failures only.

  A third adversarial review pass returned 2 more P1s (again, P2s skipped per policy), both fixed:
  - **A single repeated page wasn't strong enough evidence of the real clamp.** Round 1's fix (compare consecutive pages' own ID sets) still trusted a lone repeat — a transient cache/proxy glitch serving the previous page's content again would satisfy it just as well as genuine terminal pagination, and with the 100-listing floor, a coincidence as early as page 2 could pass it while covering a tiny fraction of the real ~5,647-listing corpus. Fixed: a candidate stop is no longer trusted on its own — `discoverAllListings` now confirms it with an independent probe at `page + CLAMP_CONFIRMATION_PROBE_OFFSET` (20; RECON_NOTES.md confirmed jobs.ge's clamp behavior holds not just at the next page but at several far-apart out-of-range page numbers — 19's content repeated at 20, 21, *and* 50 — so this jump is evidenced, not arbitrary). Only if the probe's content also matches is the walk marked `complete`; an unconfirmed or failed probe is treated as a fluke and the walk resumes normally.
  - **A source-wide detail-parsing break wouldn't stop reconciliation.** `discoveryOk` only ever looked at discovery-page health (`complete`, the listing-count floor) — a run where discovery itself succeeded but the DETAIL template broke, quarantining most or all discovered listings, would still be marked `completed` and let `closeMissingListings` advance closure for listings genuinely absent from that same unreliable run. Fixed: `discoveryOk` now also requires the quarantine rate (`quarantinedCount / discoveredCount`) to stay under `DEFAULT_MAX_QUARANTINE_RATE` (10%, tolerating ordinary per-listing noise while catching a genuine site-wide break) — computed after the per-listing loop finishes, since it needs the final `quarantinedCount`, unlike the other two conditions which are known right after discovery.

  A fourth adversarial review pass returned 1 more P1 (3 P2s skipped per policy — deadline-day expiry rounding, a fetch-failure-rate anomaly gate, and using `quarantined` rather than `partial` for the run status when the quarantine-rate gate trips), fixed:
  - **Even a confirmed clamp couldn't rule out a systemic pagination/caching regression.** Round 3's confirmation probe closes the "one repeated page" gap, but not a *consistent* one: if a bug or intermediary served the same 100-300 listings at every page number queried — including the distant probe — `complete`, the fixed floor, and the quarantine rate could all pass while the real ~5,647-listing corpus had effectively collapsed, none of them knowing what this source's corpus is actually supposed to look like. Fixed with `getLastCompletedCrawlRun` (`src/db/ingest.ts`): `discoveryOk` now also requires this run's `discoveredCount` to be at least `DEFAULT_MIN_RELATIVE_COVERAGE_RATIO` (50%) of the source's own most recent completed run — a check against real history a fixed floor can't express. Never blocks a source's first-ever run, which has no prior baseline to compare against.

  A fifth adversarial review pass returned 1 more P1, fixed:
  - **A single-partition collapse was invisible to the combined-total checks.** VIP is only ~10 of jobs.ge's ~5,647-listing corpus (RECON_NOTES.md), so `.vipEntries` silently breaking (e.g. the site changes that container's markup) would barely move `discoveredCount` — passing the fixed floor and the relative-collapse ratio easily, then letting every prior VIP listing quietly accumulate `missingStreak` toward closure over the following runs, exactly the failure concept §26's "VIP and standard sections are measured separately" acceptance criterion exists to catch. Fixed by persisting the breakdown for real: new `crawl_runs.vip_count`/`standard_count` columns (migration 0010, `CrawlRunSchema`/`CrawlRunCounts` updated to match) computed from each listing's already-known `.partition` tag. `discoveryOk` now also requires that if the last completed run had a non-zero count for a partition, this run's count for that same partition is non-zero too — deliberately a "went from something to nothing" check, not a fixed floor or ratio: VIP is small and genuinely variable (a source can legitimately have zero active VIP slots on a given day), so only a transition from a real prior baseline to zero is treated as suspicious, never "is currently small."

  A sixth adversarial review pass returned 1 more P1 (a P2 about avoiding repeated false reopen/expire churn for a still-indexed-past-deadline listing was skipped per policy), fixed:
  - **The exclusivity lock released before reconciliation actually committed.** Round 2's fix keyed the partial unique index on `status = 'running'` — but the first `finishCrawlRun` call flips `status` to its terminal value (so `closeMissingListings` can read it) *before* `expireOverdueListings`/`closeMissingListings` run, which silently released the lock for the entire window between "status set" and "reconciliation committed." A second invocation starting in that exact window could race the first run's still-in-flight reconciliation, reintroducing round 2's original double-counting bug in a narrower form — and a crash in that same window left a row that looked `completed` (a successful-looking run!) whose reconciliation had never actually happened. Fixed by decoupling the two concerns that `status` was conflating: a new `crawl_runs.reconciled_at` column (migration 0011) now backs the exclusivity index (`crawl_runs_one_unsettled_per_source_idx`, replacing the old status-keyed one) and is set only once a run is truly settled — at the *second* `finishCrawlRun` call (after reconciliation commits) for a normal run, or immediately in the `catch` block for a `'failed'` run, which never reaches reconciliation and never will. `status` still flips to its terminal value at the first call, unchanged — `closeMissingListings`'s own contract (round 2) didn't need to change at all.

  A seventh adversarial review pass returned 1 more P1 (a P2 about `crawl.ts` collapsing the discovered `href` and its resolved absolute form into the same `originalUrl`/`canonicalUrl` value, losing raw-provenance fidelity, was skipped per policy), fixed:
  - **Migration 0011 would fail or permanently wedge a source with real history.** Adding `reconciled_at` as a plain nullable column with no backfill left every pre-existing row `NULL` — for a source with more than one historical run, creating the new partial unique index over those duplicate `NULL` keys would fail migration outright; with exactly one, it would apply silently but leave that source locked out of every future crawl (its one historical row permanently "occupying" the unsettled slot). Fixed by backfilling `reconciled_at = finished_at` for every already-terminal (non-`'running'`) row before creating the index — safe because any such row settled before this column existed, well before the race this migration protects against was even possible. Verified directly, not just reasoned about: applied migrations 0000-0010 by hand against a scratch database, inserted two historical `completed`/`failed` rows for one source (simulating exactly the scenario above), applied the corrected 0011, confirmed both rows backfilled correctly, and confirmed a new crawl for that source could start immediately after.

- [ ] Incremental overlap and conservative closure logic implemented (an incomplete run cannot mass-close records) — conservative closure is done and now wired into a real crawl (see the orchestrator item above); incremental overlap is not: `src/db/reconcile-source-listings.ts`'s `closeMissingListings` advances missing streaks and closes listings (project decision 2026-09-04: threshold 3 consecutive misses, rejected below 2 since concept §13 requires the first miss to become `missing_suspected`, never `closed`). It takes only a `crawlRunId` and reads that run's `status`/`fullCoverage`/`startedAt`/`sourceId` from its own persisted `crawl_runs` row inside the transaction — deliberately not caller-supplied fields, after adversarial review (2026-09-04) pointed out that trusting a caller's claim about run completeness/coverage would let a caller bug bypass the "incomplete runs cannot mass-close" guarantee entirely. Only `status === 'completed'` **and** `fullCoverage === true` proceeds; anything else is a documented no-op, encoding §13/§21.3's "partial, blocked, or anomalous crawl must not advance missing streaks" as the function's own precondition. `fullCoverage` is a new `crawl_runs` column (migration 0008) set once at `startCrawlRun` time — true only when a run's discovery walked the entire listing space, not an incremental slice. Idempotent per crawl run via a new `source_listings.last_reconciled_at` column (migration 0007): every row `closeMissingListings` touches is gated on `lastReconciledAt < run.startedAt` (or never set) and stamped with `run.startedAt`, so retrying or double-invoking the function for the SAME crawl run can't re-increment `missingStreak` a second time — also caught by adversarial review (2026-09-04); `lastSeenAt` alone doesn't guard against that, since a genuinely-missing listing's `lastSeenAt` never changes between repeat calls for one run. `expireOverdueListings` handles deadline-based expiry separately and unconditionally, since a passed deadline is a definitive source-stated fact, not an absence inferred from crawl coverage — callers must run it before `closeMissingListings` so an expired listing's status change excludes it from missing-streak accounting for free. §10.1's incremental discovery (a rolling overlap window that can stop early once several consecutive pages contain only known, unchanged records) is not implemented — deferred, since jobs.ge's corpus is small and bounded enough (~19 pages, `RECON_NOTES.md`) that the orchestrator just walks every page every run and sets `fullCoverage: true` unconditionally; the overlap-window optimization can be added later without changing this module's contract.
