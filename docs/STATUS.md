- **A real design question the queue itself exposes, found by reading the actual rows rather than the function signatures.** Four listings each appear on the SAME side of **two or three** separate pending pairs — one jobs.ge listing (`დიჯითალ ოპერატორი` at თიბისი) is in three, each paired with a different hr.ge listing. `acceptDuplicateCandidate` has no guard against this: accepting one pair moves that listing into a cluster; accepting a *second* pending pair for the same listing does not fail — it silently retires the first, correct membership and moves the listing into a different cluster instead. Nothing in the codebase exercises this today (no test, no guard), because no UI has ever called this function against a queue with real fan-out. **Decided (2026-09-14): auto-resolve siblings on accept.** The moment a pair is accepted, every OTHER pending candidate sharing either listing is settled automatically rather than left open — the merge already answered the question the sibling candidate was asking, so leaving it in the queue as a live choice would let a reviewer accept it and undo the first decision by accident. Settled as `resultingDecision: 'confirmed_same', decidedBy: 'ruleset'` with evidence naming the accept that resolved it, not `'distinct'` — the sibling pair was never judged to be a different vacancy, it became moot. This needs its own function alongside `acceptDuplicateCandidate` (or a wrapper around it), inside the same transaction, and its own test planting exactly today's three-way fan-out.
- **A second, smaller question: which side moves.** Every listing lives in its own singleton opportunity until merged (verified: 410 listings, 410 live memberships today) — so accepting a pair genuinely can move either side into the other's cluster, and `acceptDuplicateCandidate`'s signature takes both `sourceListingId` and `toOpportunityId` rather than picking one. The two outcomes are equivalent in content but not in which opportunity id survives. A single deterministic rule (e.g. the earlier-`firstSeenAt` listing's opportunity always survives) removes this as a per-click decision; the alternative is exposing "which one wins" as a UI choice, which is more flexible and more to build and to explain.

### Phase 2B — cross-source deduplication (2026-09-06)

Working end to end, and **producing correct canonical opportunities from real data**.

- `src/dedupe/score-pair.ts` — weighted evidence scoring (§14.1 stage 4) and decision (stage 5), ruleset `v1`.
- `src/dedupe/run-dedupe.ts` — blocking, scoring, and persistence into `duplicate_candidates` / `opportunities` / `opportunity_source_memberships`.
- `src/normalize/text.ts` — title normalization, trigram similarity, and application-value normalization.
- `npm run dedupe` (add `--auto-link` to write memberships).

**The central design decision is selectivity, and it was measured rather than assumed.** A shared application value only counts as a per-vacancy identifier when at most 2 distinct listings carry it. Measured over the live corpus: application URLs are never shared by more than **2** listings, while one email (`info@ipkli.com`) is shared by **8**. Without this, "same contact address" would merge every vacancy an employer posts from one inbox — the corpus contains exactly that trap, with two genuinely different jobs behind one address.

Results on the live 410-listing corpus:

- Blocking reduced **83,845 all-pairs to 1,104 comparisons** — §14.1 stage 3 satisfied without `pg_trgm`, which stays the right tool for title-only fuzzy blocking later but is not needed while every real duplicate shares a contact value or employer name.
- **4 `confirmed_same`, 17 `needs_review`, 0 false merges.** The four became canonical opportunities, each linking one jobs.ge and one hr.ge listing at confidence 0.97.
- **Idempotent against live data:** a second `--auto-link` pass created 0 opportunities and 0 memberships, totals unchanged.

**The hard negative held on real data.** `...უფროსი ანალიტიკოსი` (senior analyst) and `...უმცროსი ანალიტიკოსი` (junior analyst) — same employer, titles differing by one morpheme in a long string — score **0.86** trigram similarity, above the 0.82 "strong" threshold. They remain two separate opportunities, held apart by their distinct ATS links. This is why title similarity never authorizes a merge on its own: for Georgian compound titles it is structurally unable to separate seniority levels, and §14.2's prohibition on auto-linking from title-and-employer agreement is doing real work here, not theoretical work.

Auto-linking requires **two independent signals** (a per-vacancy application link *and* title agreement) and nothing else can reach `confirmed_same`, however much weak evidence accumulates. `--auto-link` is opt-in; the default pass is read-only with respect to canonical state.

### Phase 2C — reversible, audited cluster membership (2026-09-06)

`src/dedupe/membership-review.ts`, 11 tests. This is the undo for everything `runDedupe` does automatically, and it is the reason auto-linking is defensible at all: §14.2 permits it only because a wrong merge can be corrected. Without a working reversal path the honest response would be to disable auto-linking entirely.

- `detachListing` removes a listing from a cluster; `reassignListing` moves it to another; `splitListingIntoNewOpportunity` breaks it out into its own; `resolveDuplicateCandidate` settles a review-queue pair without touching membership at all.
- **Nothing deletes a membership.** Retiring one stamps `supersededAt` and leaves the row, its evidence, its confidence and its decider intact — a DELETE would destroy exactly the record a human needs when asking why a merge happened. An emptied opportunity is likewise kept, not deleted: retired memberships still reference it and it is the evidence of a merge that was undone.
- Round-trip proven: an automatic merge can be detached and restored, and all three steps remain in the history with one live membership throughout.
- Mutation-verified: removing the retire step from `reassignListing` fails 3 tests, one of them by violating the database's own partial unique index — so the one-live-membership invariant is enforced by the schema, not only by application code.

### Incident: dedupe tests wrote canonical rows for real listings (2026-09-06)

The first version of `runDedupe` had no source scoping — it read and wrote against **every** listing in the database. The tests set up disposable sources, but the pass scanned the real corpus alongside them and created 4 opportunities and 8 memberships for genuine jobs.ge/hr.ge listings as a test side effect.

**The real-data guard did not catch it**, because it fingerprinted only acquisition tables (`source_listings`, `crawl_runs`, `crawl_cursors`, revision counts) and the new canonical tables were outside its view. A guard covering part of the writable surface gives false assurance about the rest — the same lesson as its two earlier failures, in a third form.

Both fixed: `runDedupe` takes an optional `sourceIds` scope (every test now passes it; it is also genuinely useful in production for rescoring one source pair), and the guard's fingerprint now covers `opportunity_source_memberships` and `duplicate_candidates` for real listings. The accidental rows were deleted and recreated by a deliberate `--auto-link` run.

**Residue — cleared 2026-09-14, and it was never as harmless as this line claimed.** The residue was orphan `test-source-*` rows left by test runs that errored before their cleanup hook. Two things were wrong with calling it harmless: it was **two** sources, not the four recorded here, and it was **visible in the product** — `sourceLabel` falls back to the raw slug, so both UUID-bearing slugs appeared in the board filter on `/opportunities` and `/listings`, which is the raw-identifier anti-pattern and held Phase 3B's exit gate open.

**The first version of that sweep was broken in the one case it existed for, and the commit gate caught it.** Two defects, both confirmed by running them rather than by reading:

- **P1 — it could not clean a dedupe-contaminated orphan.** `cleanupTestSource` deleted nine tables but not `duplicate_candidates`, `opportunity_source_memberships` or `organization_aliases`, and every FK into `source_listings` is `NO ACTION` (checked against the live schema, not assumed). So on an orphan whose listings had reached dedupe — exactly the recurrence described above — the sweep raised a foreign-key violation *after* committing the revision deletes, and aborted the whole suite with `No test files found, exiting with code 1`. **The proof offered for the original sweep was weaker than the claim it supported:** it planted a bare source with no listings, which never exercises this path. Reproduced by planting a source with two listings and a candidate, watching the run die, then fixing `cleanupTestSource` and watching the same fixture be swept cleanly with 652 tests green.
- **P2 — it could delete a concurrently running suite's live fixtures.** Test slugs carry no timestamp, so a prefix query cannot distinguish debris from a dead run from fixtures a second `npm test` is using right now. Fixed with Postgres **session-scoped advisory locks** rather than a staleness heuristic.

**Then the gate rejected both fixes, and was right twice more.** The pattern of this whole branch, one more time: the repair needed repairing.

- **P1 — cleaning the memberships left the canonical cluster behind.** A run interrupted after `runDedupe(..., { autoLink: true })` has already written `opportunities` and `opportunity_revisions`. Deleting only the membership orphans them, and **an orphan cluster is not inert** — `runRanking` enumerates `opportunities` with no join requiring a live member, so a test `canonicalTitle` could be scored and displayed as a genuine ranked result. That is the fabricated-data failure, reached from the other direction, and it means this file's own "an empty opportunity is inert — nothing surfaces it" was **false for ranking**. `cleanupTestSource` now removes clusters whose entire membership history is the listings being deleted, and deliberately spares two kinds: a cluster also holding a real listing (the 2026-09-06 incident made exactly those), and a legitimately emptied cluster, which §12.5 keeps as the evidence of an undone merge. Proven both ways — a planted `FAKE TEST VACANCY` cluster went 409 → 408 opportunities and was gone, while a planted cluster shared with a real listing survived with the corpus at 408 and the real-data fingerprint unmoved.
- **P2 (second round) — the first lock design left the losing run unprotected.** It took only an exclusive lock around the sweep and let a run that failed to get it proceed holding nothing, so a run that started second was invisible: a third run starting after the first exited could take the lock and sweep the second run's live fixtures. The protocol is now **shared for the run, exclusive for the sweep** — every run holds a shared lock for its whole duration, and sweeping additionally requires the exclusive one, which Postgres grants only when no *other* session holds either. A session does not conflict with itself, so holding shared does not block this run's own exclusive attempt; that was verified against this Postgres rather than assumed, as was the cross-session half. The exclusive lock is dropped as soon as the sweep finishes, so a run waiting to register is delayed by the sweep and not by the suite.

**And the gate rejected those two fixes as well — a third round, two more P1s.** Both were the same shape as the first: a delete path that did not know the whole graph.

- **P1 — `rankings` and `opportunity_decisions` were not unwound.** Both reference `opportunities` (and `rankings` also references the canonical revision), all `NO ACTION`. So a stranded cluster that had been ranked or shortlisted — the very downstream path the previous round established was reachable — failed the delete and aborted the sweep part-way through, exactly the failure that had just been fixed one table down. Now deleted first.
- **P1 — a shared cluster kept test-derived canonical state.** Sparing a cluster that also holds a real listing is right, but its `canonicalTitle` and resolved fields may have been computed *from the test revision*. Removing the membership without recomputing leaves fabricated content sitting on a real opportunity, where browsing and ranking cannot tell it from genuine source data. Shared clusters are now re-resolved through `resolveCanonicalOpportunity` — the project's own path, not a bespoke one.

Verified end to end, each claim by running it:

- A fake cluster that was **both ranked and shortlisted** is now swept cleanly: 409 → 408 opportunities, 911 → 910 rankings, 1 → 0 decisions, the suite green at 652 — where the previous version aborted the run outright.
- A cluster **shared with a real listing** survives, with the corpus still at 408 and the real-data fingerprint unmoved.
- With a simulated run holding the shared lock, the suite printed `another test run is active; skipping the orphan sweep` and left the planted fixture alone; once that run released, the next run swept it. Both locks are session-scoped, so a killed run cannot wedge them.

**A fourth round found two more, and they changed the design rather than adding another delete.**

- **P1 — the whole unwind was not transactional.** A sequence of autocommitted statements, where the membership deletes are the very thing that identifies which clusters belonged to the source. A crash or FK error after them leaves an opportunity nothing can still attribute to a test listing, so a test-derived title, revision or ranking would survive **every future sweep, permanently**. Now one transaction, with the re-resolution inside it.
- **P1 — "shared" was decided from live memberships only.** A cluster whose real membership happened to be *retired* counted as test-only, so the helper would try to delete an opportunity that the retired real membership still references — destroying genuine history and breaking its own FK on the way. Classification now counts **every** membership, live and superseded.

**What changed in the design, and what was deliberately refused.** The gate also pressed for deleting test-derived *historical* revisions and the rankings pinned to them. That was declined on purpose: §17.2 forbids destroying prior assessments and §12.5 keeps the history, so a test janitor silently rewriting a real opportunity's canonical history would be a worse failure than the one it repairs. The helper now does the defensible thing instead — it cleans the unambiguous case completely, repairs the *current* canonical revision of an entangled cluster through `resolveCanonicalOpportunity`, and then **says so loudly**, naming the opportunity ids, because a cluster holding both a test and a real listing means the 2026-09-06 contamination has recurred and deserves a human rather than a janitor's judgement. Old content cannot resurface through the ranked view regardless, since `listRankedOpportunities` already refuses rankings pinned to a superseded revision.

It warns rather than throws, and that is also deliberate: this helper runs in every test's `afterEach`, so throwing would wedge every run on pre-existing debris instead of letting each run clean what it can. The hard failure for real-data contamination remains the guard's fingerprint, which is independent of this path.

Proven against every shape, each by planting it and running the suite: a bare orphan; a dedupe-contaminated orphan; a test-only cluster that had been **both ranked and shortlisted** (409 → 408 opportunities, 911 → 910 rankings, 1 → 0 decisions); and a cluster whose real membership was **retired**, which was correctly kept, repaired and reported by id rather than deleted. 652 tests green throughout, corpus back to 2 sources / 410 listings / 408 opportunities / 15 candidates / 910 rankings every time.

**A fifth round found the sweep was cleaning the smaller half of the problem.**

- **P1 — it swept only one of four test slug shapes.** `createTestSource` makes `test-source-*`, but the adapter tests mock `hrGeSource`/`jobsGeSource` with random slugs — `crawl-test-*`, `isolation-test-*`, `reliability-*` — because `sources.slug` is UNIQUE and reusing the real slug made `ensureSourceSeeded` insert nothing (the 2026-09-06 defect that broke 20 hr-ge tests). Those rows are inserted by the adapters' own seeding code, so an interrupted adapter run left sources the sweep did not match at all. The four shapes now live in one exported constant, `DISPOSABLE_SOURCE_SLUG_PREFIXES`, which the guard reads — an allow-list rather than "anything that is not jobs-ge or hr-ge", since the latter would sweep a genuinely new board the first time one is added. Proven by planting one of each: `swept 3 orphan test source(s)`.
- **P1 — an entangled cluster whose real members were all retired could not be repaired by re-resolution.** With the test membership gone it has zero live members, so there is nothing to recompute a canonical revision from and the test-derived title stays *current* — and the reasoning that protects the other entangled clusters (a superseded revision makes `listRankedOpportunities` drop the old ranking) does not apply, because nothing superseded it. The opportunity row still cannot be deleted, since retired real memberships reference it. So the derived rows that would **surface** the fabricated title are removed instead: rankings and shortlist decisions, both recomputable, while membership history is not. Proven with a planted fake title carrying a live ranking — 1 → 0 rankings, the audit row kept, and the cluster reported by id.
- **P2 — two disposable sources sharing a cluster were misreported as real contamination.** Foreignness was judged by "is this listing in the set being cleaned", so a dedupe test that linked two of its own fixtures had the second one counted as real data: a false `console.error` and an ordinary test-to-test cluster routed through the repair path. Classification now asks what the other listing's **source** is. A cluster still held by another disposable source is left alone rather than deleted — deleting it would fail that source's own FK — and its own cleanup takes it. Proven: two test sources, one cluster, no alarm, and the cluster gone once both were swept.

**Five review rounds on one janitor, and every round found a real defect in the previous round's fix.** That is the lesson this branch keeps producing — two of the four P1s in the whole-branch review were also in code written as fixes — and it is the argument for reviewing repairs exactly as hard as features, not for treating a cleanup as too small to review.

### Phase 5A — CV matching and ranking (2026-09-06)

Taken out of order, ahead of Phase 3B (UI) and Phase 4, because it is the feature the product exists for and it needs nothing from either. `src/ranking/`, `npm run rank`.

- `profile-store.ts` — versioned candidate profiles with claims. Editing a profile bumps its version rather than overwriting, so a ranking always names the profile version it was computed against (§17.2's "never overwrite prior assessments when an input or model changes").
- `score-opportunity.ts` — deterministic, explainable scoring: every result carries its component scores and, when filtered, its hard-filter reasons. **No model call.** §17 permits ranking by rules, and a rule-based scorer that can explain itself is the right floor to add a model on top of later, not a placeholder for one.
- `run-ranking.ts` — caching keyed by (opportunity revision, profile, profile version, evaluation version). Changing any of those appends a new row instead of overwriting an old one, and a rerun with unchanged inputs is free.

An opportunity that crosses its deadline correctly bypasses the cache and is rescored — but it then writes back to the same four-column key via `onConflictDoUpdate`, overwriting the assessment made while it was still eligible. So §17.2's no-overwrite invariant holds for every input except time. Recorded rather than fixed, per the standing P2 policy; the fix is to put a time bucket in the key or stop upserting on rescore.
- Hard filters run against the **canonical** status, and `not_available` opportunities are excluded outright — a ranked list must not recommend a vacancy nobody can apply to.

**Not built: CV parsing.** Profiles are reviewed JSON, entered through the CLI. PDF/DOCX extraction is a separate problem, and §17's ranking is testable and useful without it. This is the honest gap between "Phase 5A" and "Phase 5".

### Incident: mutation testing corrupted live jobs.ge rows (2026-09-06)

**The mutation checks above damaged real data, twice.** Removing the per-source `WHERE` clause is precisely what stops a test's reconciliation reaching other sources' rows — so with it removed, test crawl runs reconciled every source in the shared dev database and moved all 310 freshly-crawled jobs.ge listings from `active` to `missing_suspected` (streak reached 2 across repeated runs).

- **No content was lost.** All 310 revisions survived, every listing kept its `currentRevisionId`, `lastSeenAt` was untouched (`closeMissingListings` does not write it), and the real crawl run row was unaffected. Repaired with one scoped `UPDATE` back to `active` / streak `0` / `lastReconciledAt` null — the exact state the run's own counts (`newCount=310, missingCount=0`) establish.
- **hr.ge escaped only by accident**, which is worth stating plainly: its listings carry the stale `lastReconciledAt` of `2026-09-07` described below, later than any test run's `startedAt`, so the idempotency guard excluded them. Pre-existing corruption is what shielded it, not any working protection.

**Guard added:** `src/db/real-data-guard.ts`, wired in as a vitest `globalSetup`. It fingerprints every real source's listings, runs, cursors and revision count before and after the whole suite, and fails the run if they differ. A `globalSetup` rather than a per-file hook because test files run in parallel — nothing inside one can observe what another wrote.

It does **not** refuse to run against a database holding real data; that is the normal state of any dev machine that has crawled, and a guard like that would just get switched off. It asserts the weaker always-true property instead: whatever real data is present, the suite must leave it byte-identical. On CI's fresh database there are no real source rows, so it is a silent no-op there — fittingly, since CI could not have caught this accident either.

**The guard was itself broken for its first two iterations, and both failures were the same shape as the bug it exists to catch:**

1. Its fingerprint SQL had a misplaced parenthesis, and a broad `catch` turned the syntax error into a constant string — identical before and after, so the guard passed silently. Now only Postgres's `42P01` (no schema yet) is tolerated; anything else throws.
2. After that was fixed it detected the change and printed loudly, but vitest reports a `globalSetup` teardown rejection as "error during close" and **still exits 0** — so CI would have gone green on a real detection. It now sets `process.exitCode = 1` explicitly.

Both were found only by deliberately probing the guard with a throwaway test that writes to a real row, then confirming exit code 1 and, after removal, exit code 0. A guard whose failure mode is "silently succeed" is worse than no guard, so verifying it was not optional.

### Stale reconciliation residue on real hr.ge rows (found 2026-09-06)
