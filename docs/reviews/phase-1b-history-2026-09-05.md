Per concept §25/§10.2: complete the bounded API-versus-HTML acquisition experiment, capture sanitized sitemap/index/detail fixtures, implement sitemap reconciliation and frequent small-index discovery, parse rich structured fields, add WAF/challenge detection and source-specific health checks.

**Milestone 1 (reconnaissance and acquisition decision) and milestone 2 (adapter implementation) are both done** — see `src/adapters/hr-ge/RECON_NOTES.md` for the full recon findings, `src/policies/hr-ge.ts` for the resulting policy update, and `src/adapters/hr-ge/` (`ng-state.ts`, `discovery.ts`, `detail.ts`, `sitemap.ts`, `challenge.ts`, `crawl.ts`) plus `src/cli/run-hr-ge-crawl.ts` for the adapter itself, built directly from `RECON_NOTES.md`'s "Implementation plan for adapter code" handoff. Three of Phase 0's 2026-09-02 findings were revisited against the live site and **overturned**, which is the point of the spike:

- **"No ordinary pagination links"** — wrong. `/search-posting?pg=N` is ordinary `<a href>` pagination, present in the raw server-rendered HTML (Phase 0 appears to have looked for `page=`/`?p=`; hr.ge's parameter is `pg=`). 100 listings per page, 33 pages, 3,265 announcements, and an out-of-range page returns a real HTTP 404 rather than clamping the way jobs.ge does.
- **"The public sitemap is useful for reconciliation"** (concept §5.2/§10.2's stated default strategy) — wrong for this source, and the most consequential finding here. Measured against a full 33-page index walk, the sitemap contains **exactly the 1,075 paid/priority announcements and zero free ones** (`isPriority: true` correlates with sitemap membership perfectly in both directions across all 3,263 recovered IDs) — roughly 33% of the live corpus, with no `lastmod` anywhere in the file. Using it as the reconciliation oracle would make 2,190 free listings look absent on every *healthy* run and mass-close them, which is precisely the failure §10.2's "never infer mass closure from a single reduced result set" exists to prevent. Demoted to an additive cross-check that can only ever introduce candidate IDs, never evidence absence. The index walk is the reconciliation source instead.
- **"No confirmed public listing/search JSON API"** — half right. No *client* XHR carries listing content (favorites and banners remain the only ancillary calls, as Phase 0 said), but the server-rendered HTML embeds Angular's `ng-state` transfer island, which names the upstream endpoints outright and carries their verbatim JSON response bodies. So the endpoints were identified without ever calling them, then evaluated and rejected on their merits — see the acquisition decision below.

Two further findings worth carrying forward: hr.ge publishes a quantitative rate limit in response headers (`Ratelimit-Policy: 20;w=60`, one request per 3s) where robots.txt declares no `Crawl-delay`, now recorded in the policy; and detail pages set `hideContactPerson: true` while still shipping the recruiter's name, personal email and mobile inside the JSON island, so the parser must honor that flag and the `show*` flags rather than ingesting what the source deliberately hides (the committed fixtures redact those values).

  A first `/codex:adversarial-review --base main` pass (2026-09-05, run after the Codex CLI's usage quota reset) returned 2 highs and 2 mediums; per this project's severity-gate policy (P2s skipped 100%, no case-by-case judgment) the 2 highs were fixed, the 2 mediums deferred:
  - **A healthy 200 response with an exhausted rate-limit header was discarded as a retry.** `classifyHttpResult` checked `isHrGeRateLimited` before the status check, so a real, successfully-fetched response whose headers merely reported `Ratelimit-Remaining: 0` classified as `'retry'` and was never parsed — "you've used your last allowed request" is not the same claim as "this response is invalid." Fixed by checking status 200 first (after the WAF-challenge check, which must still take priority regardless of status); only a genuinely rejected request (429) reaches the rate-limit branch now. Also fixed the related politeness gap the same finding raised: the per-listing detail loop previously kept firing at every remaining listing at the same cadence even after a genuine 429, contradicting concept §6.2's "honor... retry instructions" — a `'retry'` outcome now stops the loop for the rest of the run instead of continuing, leaving the un-attempted listings for a later run.
  - **A failed sitemap-only fetch was recorded as a positive sighting.** The per-listing loop's failure branch called `touchSourceListingSeen` unconditionally, including for a candidate recovered only from the sitemap cross-check (never observed in this run's own index walk). Since the sitemap carries no `lastmod` and can retain a removed listing indefinitely, a stale sitemap entry whose detail page then 404s would have its `lastSeenAt` bumped and `missingStreak` reset on every run purely from the stale sitemap re-nominating it — permanently blocking a genuinely-removed listing from ever reaching `missing_suspected`/`closed`. Fixed by tracking which ids came from the sitemap cross-check (`sitemapOnlyIds`) and skipping `touchSourceListingSeen` for a failed fetch on one of them; only a listing this run actually observed in the index gets that protection. Both fixes proven with 3 new regression tests in `crawl.test.ts`, each independently confirmed to fail against the pre-fix code (via `git stash` on just `crawl.ts`) before the fix was restored, per this project's own established practice for regression tests.
  - Deferred (P2, policy): the `allowedHosts` policy field the previous commit added has no corresponding `source_policies` column/migration, so `ensureHrGeSourceSeeded`'s persisted policy row cannot represent it; and there is no separate bounded-page incremental-discovery mode, so the exit gate's "frequent small-index discovery" claim above overstates what's actually invokable today (discovery always walks to the 404 terminator) — both left for a future pass.

  Committing the round-1 fixes above through the real (no-longer-quota-exhausted) pre-commit gate itself caught a further P1 the review had missed: **the 429-abort fix could still let a run complete and wrongly advance closure on listings it never attempted.** The gate's own review reasoned correctly that on a large corpus, a single 429 (incrementing `failedCount` by exactly 1) never approaches `maxFetchFailureRate`'s 50% ceiling regardless of how many of the remaining discovered listings were left completely untouched by the early `break` — so `discoveryOk`'s existing ratio-based guards could all pass, the run gets marked `completed`, and `closeMissingListingsInTransaction` then advances every one of those never-attempted (not merely failed) listings toward `missing_suspected`/`closed` purely for having never been asked about, directly violating this project's own exit-gate guarantee that "incomplete runs cannot mass-close records." Independently confirmed against the actual code before fixing (the same "verify before acting on the report" step every prior review round in this project has used) — the earlier round-1 fix's own comment claiming "the health guards below already treat a materially incomplete run as 'partial'" was checked and found to be an unverified assumption, not something the code actually did. Fixed with a new `detailFetchAbortedByRateLimit` flag, set the moment a `'retry'` outcome breaks the per-listing loop and required (`!detailFetchAbortedByRateLimit`) alongside every existing `discoveryOk` condition — unconditionally disqualifying the run from `'completed'` regardless of what the ratio-based guards alone compute, closing the exact gap independent of corpus size. Proven with a fourth regression test (10-listing corpus, a single 429 on the first listing aborting the other 9 as genuinely unattempted, not merely failed — the existing 50%/10% ratio guards pass on their own with room to spare) — confirmed to fail against the code with only this specific guard removed (not the whole file reverted, to isolate it from the two round-1 fixes) before being restored.

  Committing THAT fix through the gate caught one more P1 (round 3): **the clean 429 abort prevents wrong reconciliation, but says nothing about whether the corpus's tail ever gets covered at all.** `rotatedListings` always started from `listings.values()`'s own insertion order — the index walk's own `renewalDate ?? publishDate`-descending order, RECON_NOTES.md, which changes slowly run to run, especially near an established corpus's tail — so if the same rate-limit boundary recurs at roughly the same request count every run (plausible: discovery's own ~33 index-page fetches already spend part of the same `Ratelimit-Policy` budget before the detail loop even starts), every run would keep succeeding on the identical prefix and never make progress past that point, indefinitely. First fix: rotate the per-listing loop's starting point by an offset derived from the run's own `startedAt` (`Date.parse(startedAt) % orderedListings.length`).

  Committing THAT fix caught two more P1s and a P2 (round 4) — the wall-clock rotation itself was disproven with a concrete counterexample:
  - **A wall-clock-derived rotation offset cannot guarantee eventual full coverage under periodic scheduling.** Under an exactly periodic schedule (e.g. a fixed daily cron time), the sequence of offsets `Date.parse(startedAt) % length` visits over time is itself periodic with period `length / gcd(dailyStepMs, length)` — whenever that gcd exceeds 1, entire residue classes of the corpus are never reached, no matter how many runs pass. Independently confirmed against the actual arithmetic before accepting the report. Fixed by replacing the wall-clock formula with a genuinely persisted cursor: a new nullable `crawl_runs.next_cursor_source_record_id` column (migration `0012_living_mastermind.sql`, `CrawlRunSchema` updated to match) records the `sourceRecordId` of the last listing THIS run attempted (success or failure alike, tracked via `lastAttemptedSourceRecordId`, set at the top of each loop iteration so a mid-iteration `break` still counts); the next run reads it back via a new `getMostRecentCrawlRun` query (deliberately not status-filtered — unlike `getLastCompletedCrawlRun`, a `'partial'` run's own cursor progress is still real progress worth resuming from, and requiring `'completed'` would mean a source stuck under a persistent rate limit could never advance its cursor at all) and resumes from that position, wrapping around — **round 5 (below) later corrected this to resume AT the cursor, not after it; the "after" behavior described here was itself a bug.** `finishCrawlRun`'s signature grew an optional `nextCursorSourceRecordId` param (omitted entirely — not just left undefined — means "don't touch this column," so jobs.ge's own calls, which never pass it, leave the field permanently null for that source without needing to know it exists). Consecutive runs under an identical recurring rate-limit pattern now provably reach listings the first run never touched at all — proven directly (not just reasoned about) with a two-run regression test using a fake rate limiter that rejects after a fixed request *count* regardless of URL: run 2 resumes past run 1's persisted cursor and reaches two listings run 1 never attempted. That test itself needed a second pass: its first draft used `.not.toBeNull()` on an absent row's `currentRevisionId`, which is `undefined`, not `null` — `undefined !== null` made that assertion pass regardless of whether the fix worked, caught by deliberately disabling the fix and finding the "pre-fix" run still green; fixed by asserting the row itself `toBeDefined()` first.
  - **A transient sitemap-only failure was treated exactly like a confirmed 404.** The round-1 fix skipped `touchSourceListingSeen` for ANY failed detail fetch on a sitemap-only-recovered candidate, uniformly — but RECON_NOTES.md's own documented pagination-shift race means a sitemap-only candidate can be a perfectly live, active listing the index walk simply missed by chance this run; for that case, a merely transient failure (timeout, 5xx, a WAF `'blocked'`/rate-limit `'retry'` classification) is not evidence of absence the way a definitive HTTP 404 is, and deserves the same protection an ordinary index-observed listing's own transient failure already gets. A small number of such unlucky transient failures could otherwise still clear `discoveryOk` and let reconciliation advance a genuinely-active listing's missing streak toward closure. Fixed by narrowing the skip condition to `sitemapOnlyIds.has(id) && fetchResult?.status === 404` specifically — only a confirmed 404 withholds the protection now; any other failure reason calls `touchSourceListingSeen` same as before. Proven with a new regression test (a sitemap-only candidate whose detail fetch fails with a plain network error, not a 404) confirmed to fail against the code with the 404-specific check widened back to "any sitemap-only failure" before being restored.
  - Deferred (P2, policy): a healthy 200 with `Ratelimit-Remaining: 0` is correctly parsed as success (round 1) but the very next request still fires after the ordinary 3-second delay rather than waiting out the rate-limit reset window, which can turn an otherwise-healthy crawl `'partial'` on the very next request — left for a future pass, alongside the two round-1 P2s.

  Committing THAT fix caught two more P1s (round 5) — the persisted cursor from round 4 was itself wrong in two ways, both found by simulating the exact scenario before trusting the report, the same way round 4's own gcd counterexample was verified:
  - **Resuming AFTER the rejected listing could lock specific listings out forever, not just delay them.** Simulated directly (not just reasoned about): 8 stable listings, a rate limit allowing exactly 3 successes before every 429 — "resume after the rejected item" settles into a stable 2-run cycle for this corpus-size/success-count combination, where whichever listing always lands in the 4th position of its lap is skipped every single time, forever (items 4 and 8 in the simulation). This is the exact same class of bug round 4 fixed for the wall-clock version, just relocated into the cursor's own resume-point arithmetic rather than removed. Fixed by resuming AT the rejected listing instead of after it — retrying it as the very first attempt of the next run rather than perpetually skipping past it; the same simulation with this change reaches full 8-listing coverage by the third run. Proven with a regression test reproducing that exact 8-listing/3-success scenario across three consecutive runs, confirmed to fail (wrong cursor trajectory) with the offset formula reverted to "after" before being restored.
  - **A run that made zero progress explicitly wiped out a real prior cursor instead of preserving it.** Each run's `crawl_runs` row is a brand-new INSERT, not a continuation of the previous run's row — "omit the field so `finishCrawlRun` doesn't touch the column" (round 4's assumption) only preserves a value within one run's own two settlement calls on the SAME row; it does nothing for a value that needs to carry forward into a DIFFERENT (this run's own, freshly-inserted) row, which starts NULL regardless. A run whose discovery itself got rate-limited before the per-listing loop ever ran (so `lastAttemptedSourceRecordId` stayed `null`) therefore persisted `null` as its own cursor, discarding a perfectly good prior cursor and silently resetting the corpus to the head — recreating the exact starvation this whole mechanism exists to prevent, just triggered by a discovery-level rate limit instead of a detail-level one. Fixed by explicitly copying `previousRun.nextCursorSourceRecordId` forward into this run's own row whenever no listing was attempted at all, rather than treating "nothing to report" and "omit the field" as equivalent. Proven with a regression test (discovery rate-limited on page 1, zero listings ever reached) confirmed to fail (cursor reset to `null`) against the naive "always persist `lastAttemptedSourceRecordId`" version before being restored.

  Committing THAT fix caught two more P1s (round 6). At this point the user asked, reasonably, why review kept finding new issues each round — the per-commit gate only ever reviews one commit's diff at a time, so each fix's own narrow diff gets scrutinized in isolation, not the cumulative cursor design as a whole; the user chose to invest in a structural fix rather than another narrow patch, which is what this round actually did:
  - **A sitemap-only response that was both a 404 AND explicitly WAF-blocked still counted as confirmed absence.** `isDefinitiveSitemapOnlyAbsence` checked only `fetchResult?.status === 404`, but `classifyHttpResult` (challenge.ts) checks the WAF-challenge signal before falling back to plain status handling — a response can carry status 404 while `outcome` is `'blocked'`, which is evidence of a block, never evidence of absence. Fixed by requiring `outcome === 'failure'` (never `'blocked'`/`'retry'`) in addition to the 404 status.
  - **`crawl_runs`-column cursor storage (rounds 4-5) had a structural gap no amount of case-by-case patching was closing: each run's row is a brand-new INSERT, so "did anything change" had to be inferred from that one run's own state, and a TRUNCATED discovery walk (some index pages failed, so the discovered set never reached the real cursor's position) that then fully processed its own partial set — no rate-limit abort — still matched round 5's "loop finished, no abort → reset to null" condition, discarding a real prior cursor for work that never represented a genuine full sweep.** Rather than add a fourth special case, replaced `crawl_runs.next_cursor_source_record_id` (migration `0012_living_mastermind.sql`, this session's own not-yet-committed work) entirely with a dedicated single-row-per-source `crawl_cursors` table (migration `0012_high_abomination.sql` — the column-based migration was deleted outright and regenerated fresh, safe because it had never been committed to git through five straight blocked commit attempts) plus `getCrawlCursor`/`setCrawlCursor` (`src/db/ingest.ts`). The table is read once after `startCrawlRun`'s exclusivity lock is acquired (also closing a related P2 the same round raised: reading the predecessor *before* the lock left a handoff-race window) and written to in exactly two cases — a rate-limit rejection (write the rejected listing), or a **genuinely complete** full sweep (`complete`, from `discoverAllListings` — not just "the loop finished without a 429," closing the truncated-discovery gap specifically). Every other code path (zero listings, a truncated walk that never aborted, a thrown error) now calls neither function at all, which — because the row isn't recreated every run — means "preserve the real value" by construction rather than something each caller has to remember to special-case (also closing a third related P2, about a failed run's own null-cursor row shadowing the real one: with a dedicated table, a failed run simply never writes to it). Proven with 2 new regression tests (a WAF-blocked-but-404 sitemap-only response; a truncated discovery walk whose partial result gets fully processed), each confirmed to fail against the code with just its own guard condition removed before being restored — plus every existing round 4/5 cursor test updated to read the new table (`getCursor()`) instead of a `crawlRun` field, unchanged in what they actually assert.
